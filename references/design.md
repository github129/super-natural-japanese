# 設計リファレンス

言い回しを直す前に、文章の骨組みを決める。AI臭さの大半は、個々の表現ではなく「誰にも向いていない、型どおりの骨組み」から生まれる。

## 1. 設計メモの書き方

本文の前に、次の四行を書く（頭の中でもよいが、長文や重要な文書では実際に書く）。

```
読み手と場面：Googleスプレッドシートを知らない一般の社会人（依頼に指定なし）
主メッセージ：Excelで作っている表を、作り直さずに複数人で同時に編集できる
問いの順番：何それ？ → 今のExcelの表はどうなる？ → 何が違う？ → 足りないものは？
具体の粒度：読み手が広いので「集計や名簿の管理」程度にとどめる
```

主メッセージが一文で書けないときは、書き方ではなく素材の問題である。何を伝えたいのかをユーザーに確かめるか、材料を集める。材料がないまま書き始めると、「さまざまな」「重要な」で空白を埋めることになる。

## 2. 骨組みは「読み手の問いの連鎖」で作る

各文は、直前の文を読んだ読み手が抱く疑問に答える。「〜ので、〜」のような因果のつながりが自然に生まれ、型にも演出にも頼らなくてよくなる。

型（定義 → 列挙 → 強み → 注意）は、書き手が埋める枠である。問いの連鎖は、読み手の頭の中の順番である。前者は誰に向けても同じ形になり、後者は読み手ごとに変わる。

## 3. 情報の位置づけ

人が書いた説明には、書き手とその情報との関係がにじむ。「もともとブラウザで軽く使う表計算として始まったので、Excelの高度な機能まで全部あるわけではありません」の「もともと」は、書き手がこの製品の経緯を知っていて、機能の限界がその出自から来ていると示している。読み手はそこから、製品の全体像と、どの情報が中心でどれが補足なのかを受け取る。

AIの文章は、事実をすべて同じ重さの属性として並べやすい。「〜できます。〜できます。〜も使えます。」と、どれが中心でどれが最近の追加なのかが消え、カタログのようになる。つなぎも「また」「さらに」「加えて」の足し算になりやすい。

直すときは、その事実が実際にどういう位置にあるかを考える。

- 時間：もともと〜、最近は〜、以前は〜だったが今は〜
- 意外さ：〜と思われがちだが、実際は〜
- 因果：〜なので、〜
- 重さ：中心の話と、補足の話を分ける

**これは言い回しの規則ではない。** 「最近は」「実は」を足せば自然になるわけではなく、事実と違う位置づけを書けば、かえって嘘っぽくなる。位置づけが分からないときは、調べるか、無理に付けずに書く。

## 4. 具体の粒度

- 読み手が自分の状況に当てはめられる粒度で書く
- 読み手が広いときに一つの場面へ絞ると、多くの読み手にとって他人事になり、場面そのものが作り物に見える
- 読み手が絞れているとき（「工場の係長向けに」など）だけ、一つの場面を深く書く
- 架空の場面をこしらえない。実際にありそうな用途を、読み手の言葉で言う

## 5. 型と演出の見分け方

骨組みを一行ずつ並べ、次の型に当てはまっていないか見る。当てはまっていたら、主メッセージに関係しない枠を外す。

| 文章 | AIが流れやすい型 | 外し方 |
|---|---|---|
| 紹介文 | 定義 → 機能の列挙 → 強み → ただし → コツ | 場面を一つ見せ、注意は本当に必要なものだけ |
| 解説記事 | 問いかけ → 三点の列挙 → 同じことを繰り返すまとめ | 答えから書き、まとめは次の行動にする |
| 報告 | 背景 → 課題 → 対策 → 今後の展望（全部同じ厚さ） | 読み手が判断に使う節を厚くする |
| メール | 挨拶 → 経緯の長い説明 → 依頼 → 締めの挨拶の重ね | 依頼を先に。経緯は必要な分だけ |
| 議事録 | 発言の時系列の書き起こし | 決定事項と宿題を先頭に |

「強み」「注意」「まとめ」「今後の展望」は、内容が求めるときだけ置く。どの文章にも付いている枠は、読み手には飛ばされる。

型を避けようとして、別の演出に流れることもある。

| 演出 | 例 |
|---|---|
| 読み手を呼びかけで絞る | 毎朝、紙の点検表で設備を確かめている職場なら |
| 主語のない短文でリズムを作る | プログラムはほとんど書きません。／コツは一つ。 |
| 架空の場面を細かく描く | 異常があればその場で写真を添えて報告でき… |

## 6. 実例：Googleスプレッドシートを紹介する200字の台本

**型どおりの版**（設計なし）

> Googleスプレッドシートは、Googleが提供する表計算ソフトです。売上の集計や名簿の管理、シフト表の作成など、Excelでできることをブラウザで行えます。複数人で同時に編集できるのが強みです。作った表はスマホからも見られます。Excelのファイルをそのまま開いて編集することもできます。

定義 → 列挙 → 強み → 追加機能の型。文と文がつながっておらず、どの読み手にも向いていない。

**演出に流れた版**（読み手を勝手に絞り、場面をこしらえた）

> Googleスプレッドシートは、Googleの表計算ソフトです。毎月、各店舗からExcelを集めて売上をまとめている経理なら、その作業を一枚の共有シートに置き換えられます。各店が直接入力し、合計はその場で更新されます。ファイルを送り合う必要はありません。慣れたExcelの関数も、そのまま使えます。

「具体を一つ」を満たすための架空の場面、「〜経理なら」の呼びかけ、主語のない短文。型は外れたが、広告の語り口になった。

**自然な版**（問いの連鎖で書いた）

> Googleスプレッドシートは、Googleが提供する表計算ソフトです。ブラウザで開くので、同じ表を離れた場所にいる数人で同時に編集できます。Excelのファイルもそのまま開け、関数の多くはExcelと同じ書き方なので、今使っている表を作り直す必要はありません。もともとブラウザで軽く使う表計算として始まったので、Excelの高度な機能まで全部あるわけではありませんが、集計や名簿の管理には十分です。

何それ？ → 何が違う？ → 今の表はどうなる？ → 足りないものは？の順に一文ずつ答えている。具体は読み手全体が当てはまる粒度で、演出がない。最後の文の「もともと」は、機能の限界が製品の出自から来ているという事実をそのまま示していて、機能の列挙にも弁解にも見えない。

この例は「書き方」を示すためのもので、答えの雛形ではない。別の題材でこの文を流用したり、同じ題材の依頼にこの文をそのまま返したりしない。

## 7. リライトでの設計

既存の文章を直すときも、まず元の文章から四行を読み取る。

- 主メッセージが読み取れない → 表現ではなく構成から直す必要がある。ユーザーに確認してから大きく直す
- 主メッセージは明確で、表現だけが問題 → 設計はそのまま、問題箇所だけ直す

### keep / change の割り振り

直す前に、元の文を一行ずつ(長い文書なら段落ごとに)並べ、それぞれに keep か change を付ける。既定は keep。change にするのは、直すことで読み手の得を一言で言える箇所だけにする。「分かりやすく書き直して」のように依頼が文章全体を求めているときは、構成そのもの(見出しを立てる、並列の項目を箇条書きにする、連絡先を独立させる)も change の候補に入る。

```
keep    お世話になっております。田中です。
change  いつもお世話になっております。          → 挨拶の重複。削る
keep    先日はお忙しい中、お時間をいただきありがとうございました。
change  添付の資料をご確認してください。        → 謙譲語の誤用。「ご確認ください」
keep    なお、見積金額は税込みで1,250,000円となります。
```

この表があると、直し終えたときに「change の数」と「変更の種類」を数えられる。同じ種類の変更が全項目に及んでいたら、掃引になっている。個々の修正が正しくても、均質に直された文章は元より不自然に見える。良い箇所は触らず、最小の差分で最大の価値を足すのが、自然さを保ったまま質を上げる直し方になる。

### 型どおりの元文を直すとき

元の文が「定義 → 列挙 → 強み → ただし → コツ」の型そのものなら、言い回しを直しても型は残る。依頼が「AIっぽさを消して」「自然にして」のように文章全体の質を求めているときだけ、文の順番を組み替えてよい。骨組みを一行ずつ並べ、読み手の問いの順(何それ？ → 自分に何ができる？ → 今のやり方を変える必要は？)に並べ直してから、言い回しを直す。ただし事実は足さず、元の事実はすべて残す。字数のために削るなら、言い回しから削る。

**元の文**（型そのもの）

> 電子契約は、契約書をオンラインで取り交わす仕組みです。押印や郵送が不要になり、契約の締結を数日から数分に短縮できます。主な特徴は次の3つです。1. 印紙税がかからない 2. 契約書の保管と検索が簡単 3. 相手方はアカウント登録なしで署名できる。ただし、一部の契約は法律で書面が求められます。コツは一つ。まず社内の定型契約から始めることです。

骨組みを並べると、定義 → 効果 → 特徴 3 点 → ただし → コツ。事実は 7 つ（定義、時間短縮、印紙税、保管と検索、相手方の登録不要、書面が必要な契約、定型契約から）。

**組み替えた文**（事実は 7 つとも残し、順番だけ読み手の問いに沿わせた）

> 電子契約は、契約書をオンラインで取り交わす仕組みです。押印と郵送がなくなるので、これまで数日かかっていた締結がその日のうちに終わります。相手方はアカウントを作らなくても署名でき、締結後の契約書は検索できる形で保管されます。紙より安く済むのは、印紙税がかからないためです。法律で書面が求められる契約は残るので、まずは社内の定型契約から移すと無理がありません。

何それ？ → 何が変わる？ → 相手に負担は？ → 費用は？ → 全部移せる？の順。「主な特徴は3つ」「ただし」「コツは一つ」の枠を外し、印紙税の事実は「安く済む理由」として、書面の例外は「定型契約から始める理由」として、それぞれ前の文とつないだ。列挙だった事実が、理由と結果の関係で並び直っている。

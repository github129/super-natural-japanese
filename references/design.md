# 設計リファレンス

言い回しを直す前に、文章の骨組みを決める。AI臭さの大半は、個々の表現ではなく「誰にも向いていない、型どおりの骨組み」から生まれる。

## 1. 設計メモの書き方

本文の前に、次の四行を書く（頭の中でもよいが、長文や重要な文書では実際に書く）。

```
読み手と場面：Power Appsを知らない一般の社会人（依頼に指定なし）
主メッセージ：紙やExcelの業務を、プログラムなしでアプリにできる
問いの順番：何それ？ → 何ができる？ → 今の仕組みを変える必要は？ → 作るのは難しい？
具体の粒度：読み手が広いので「申請や点検の作業」程度にとどめる
```

主メッセージが一文で書けないときは、書き方ではなく素材の問題である。何を伝えたいのかをユーザーに確かめるか、材料を集める。材料がないまま書き始めると、「さまざまな」「重要な」で空白を埋めることになる。

## 2. 骨組みは「読み手の問いの連鎖」で作る

各文は、直前の文を読んだ読み手が抱く疑問に答える。「〜ので、〜」のような因果のつながりが自然に生まれ、型にも演出にも頼らなくてよくなる。

型（定義 → 列挙 → 強み → 注意）は、書き手が埋める枠である。問いの連鎖は、読み手の頭の中の順番である。前者は誰に向けても同じ形になり、後者は読み手ごとに変わる。

## 3. 情報の位置づけ

人が書いた説明には、書き手とその情報との関係がにじむ。「最近は、Copilotに説明すると画面の土台まで用意してくれます」の「最近は」は、書き手がこの製品の経緯を知っていて、この機能が新しく加わったものだと示している。読み手はそこから、製品の全体像と、どの情報が新しいのかを受け取る。

AIの文章は、事実をすべて同じ重さの属性として並べやすい。「〜できます。〜できます。〜も使えます。」と、どれが中心でどれが最近の追加なのかが消え、カタログのようになる。つなぎも「また」「さらに」「加えて」の足し算になりやすい。

直すときは、その事実が実際にどういう位置にあるかを考える。

- 時間：もともと〜、最近は〜、以前は〜だったが今は〜
- 意外さ：〜と思われがちだが、実際は〜
- 因果：〜なので、〜
- 重さ：中心の話と、補足の話を分ける

**これは言い回しの規則ではない。** 「最近は」「実は」を足せば自然になるわけではなく、事実と違う位置づけを書けば、かえって嘘っぽくなる。位置づけが分からないときは、調べるか、無理に付けずに書く。

## 4. 具体の粒度

- 読み手が自分の状況に当てはめられる粒度で書く
- 読み手が広いときに一つの場面へ絞ると、多くの読み手にとって他人事になり、場面そのものが作り物に見える
- 読み手が絞れているとき（「工場の係長向けに」など）だけ、一つの場面を深く書く
- 架空の場面をこしらえない。実際にありそうな用途を、読み手の言葉で言う

## 5. 型と演出の見分け方

骨組みを一行ずつ並べ、次の型に当てはまっていないか見る。当てはまっていたら、主メッセージに関係しない枠を外す。

| 文章 | AIが流れやすい型 | 外し方 |
|---|---|---|
| 紹介文 | 定義 → 機能の列挙 → 強み → ただし → コツ | 場面を一つ見せ、注意は本当に必要なものだけ |
| 解説記事 | 問いかけ → 三点の列挙 → 同じことを繰り返すまとめ | 答えから書き、まとめは次の行動にする |
| 報告 | 背景 → 課題 → 対策 → 今後の展望（全部同じ厚さ） | 読み手が判断に使う節を厚くする |
| メール | 挨拶 → 経緯の長い説明 → 依頼 → 締めの挨拶の重ね | 依頼を先に。経緯は必要な分だけ |
| 議事録 | 発言の時系列の書き起こし | 決定事項と宿題を先頭に |

「強み」「注意」「まとめ」「今後の展望」は、内容が求めるときだけ置く。どの文章にも付いている枠は、読み手には飛ばされる。

型を避けようとして、別の演出に流れることもある。

| 演出 | 例 |
|---|---|
| 読み手を呼びかけで絞る | 毎朝、紙の点検表で設備を確かめている職場なら |
| 主語のない短文でリズムを作る | プログラムはほとんど書きません。／コツは一つ。 |
| 架空の場面を細かく描く | 異常があればその場で写真を添えて報告でき… |

## 6. 実例：Power Apps を紹介する200字の台本

**型どおりの版**（設計なし）

> Power Appsは、Microsoftが提供する業務アプリの作成ツールです。申請フォームや在庫管理、点検記録など、社内で使うアプリをプログラムをほとんど書かずに作れます。ExcelやSharePoint、Teamsとつなげられるのが強みです。作ったアプリは、パソコンでもスマホでも使えます。Copilotに日本語で頼めば、アプリのたたき台も作れます。

定義 → 列挙 → 強み → 追加機能の型。文と文がつながっておらず、どの読み手にも向いていない。

**演出に流れた版**（読み手を勝手に絞り、場面をこしらえた）

> Power Appsは、Microsoftの業務アプリ作成ツールです。毎朝、紙の点検表で設備を確かめている職場なら、それをスマホの入力画面に置き換えられます。異常があればその場で写真を添えて報告でき、結果はExcelの表にそのまま残ります。プログラムはほとんど書きません。作りたい画面をCopilotに日本語で伝えると、たたき台ができあがります。

「具体を一つ」を満たすための架空の場面、「〜職場なら」の呼びかけ、主語のない短文。型は外れたが、広告の語り口になった。

**自然な版**（問いの連鎖で書いた）

> Power Appsは、Microsoftが提供する業務アプリの作成ツールです。紙やExcelで回している申請や点検の作業を、プログラムをほとんど書かずにスマホのアプリにできます。データはSharePointやExcelにそのまま置けるので、今の仕組みを大きく変えずに始められます。最近は、作りたいアプリをCopilotに日本語で説明すると、画面の土台まで用意してくれます。

何それ？ → 何ができる？ → 今の仕組みは？ → 作るのは難しい？の順に一文ずつ答えている。具体は読み手全体が当てはまる粒度で、演出がない。最後の文の「最近は」は、Copilot の機能が後から加わったという事実をそのまま示していて、機能の列挙に見えない。

## 7. リライトでの設計

既存の文章を直すときも、まず元の文章から四行を読み取る。

- 主メッセージが読み取れない → 表現ではなく構成から直す必要がある。ユーザーに確認してから大きく直す
- 主メッセージは明確で、表現だけが問題 → 設計はそのまま、問題箇所だけ直す
